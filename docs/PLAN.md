## 1. 项目名

### 1.1 命名标准（先立三条，再选名）

1. **第一眼就要看见「译」或「中文」**——用户不知道你在做什么，名字必须自己说。这一条是硬性的，不满足直接淘汰（原「馬譜」就是栽在这里：谱=名录/血统，不指向"译名"）。
2. **能装在口头上**——2～4 字，念一遍不拗口，简繁都成立。
3. **能长大**——今天只有马名，明天要装赛事名、骑师名、练马师名，名字不能被"马名"锁死。

### 1.2 候选（按"第一眼直白度"排序）

| 候选 | 第一眼 | 好记 | 覆盖范围 | 主要问题 |
| --- | :---: | :---: | --- | --- |
| **马名译典** | ★★★★★ | ★★★☆ | 只覆盖"名" | 像工具书，品牌感弱；但最不可能被误解 |
| **赛马译典** | ★★★★★ | ★★★☆ | 马名+赛事+人物全覆盖 | 四字偏正式，念起来像出版物 |
| **马名通译** ✅ | ★★★★★ | ★★★★ | 只覆盖"名" | **已选**。「通译」有职司感，稍老派；覆盖面靠副标题补 |
| **马名译馆** | ★★★★ | ★★★★ | 可扩到赛事/人物 | 「馆」暗示有实体，做纯网站略重 |
| **译马录** | ★★★★ | ★★★★★ | 可扩 | 古籍腔，年轻用户可能觉得"文" |
| **马名有译** | ★★★★ | ★★★★ | 只覆盖"名" | 像 slogan 多过像站名 |
| **中文马名** | ★★★★★ | ★★★★ | 只覆盖"名" | 极致直白，但像栏目名，不像品牌 |
| **骏译** | ★★★☆ | ★★★★★ | 可扩 | 两字最好记、域名最好拿；「译」被「骏」修饰，需半秒联想 |

### 1.3 我的选择

**站名用「马名通译」，副标题「全球赛马中文名典」。**

选它的理由，正好对上三条标准：

- **第一眼就懂**：`马名` + `通译` 两个词都在说事——"马的名字"、"翻译"。不用猜。
- **好念好写**：四字，声调 3-2-1-4，念着顺；繁体「馬名通譯」字形对称。
- **能长大**：`通译` 不只管马名——赛事名、骑师名、练马师名都是"通译"的对象。比「马名译典」的"典"字更活。
- **气质对**：「通译」是旧时对译员的称呼（随行通译、通译官），有职司感，不像工具书，也不像博彩。

页面 `<title>` 模板：

```
名將田原（メイショウタバル / Meisho Tabaru）· 马名通译
```

搜索结果里同时出现中文名、原名、站名，长尾词一网打尽。

> 域名注意：**不要用 `tongyi` 单独做域名**——与阿里「通义」系列撞名（通义千问），SEO 和商标都吃亏。用 `mamingtongyi.com`，或更短的 `maming.racing`。

### 1.4 命名红线

- 不出现「香港賽馬會」「HKJC」作为站名或主视觉（可作数据来源署名）。
- 不出现「马经」「贴士」「心水」「赔率」「推荐」等博彩导向词。
- 不用「官方」「权威认证」自称；用「港译来源：香港赛马会公告」这类**具体署名**。
- **避开「译马」**：与「驿马」（驿马星、驿马动）同音，会被读成占卜/物流。
- **避开「译林」**：译林出版社是知名商标，`马名译林` 这类名字有混淆与商标风险。
- 定名后先查商标（第 41 类教育娱乐 / 42 类网站服务 / 16 类印刷品）与域名，再定 logo。

## 2. 为什么这件事值得做

### 2.1 中文世界缺的是"主键"，不是"内容"

现在中文用户查一匹外国马，路径是：百度/小红书搜中文名 → 搜不到 → 猜英文名 → Google → netkeiba / Racing Post → 看日文英文 → 自己脑内翻译。断点在**名称没有稳定的对应关系**。

- 香港赛马会已经做了三十年人工翻译，这是事实上的中文标准（港译）。
- 但这批译名**只存在于 PDF/Word 附件里**，搜不到、链不了、结构化不了。
- 大陆媒体各译各的（「名將田原」/「名将田园」/「Meisho Tabaru」），同一匹马三个名字。

**谁把这层对齐做出来，谁就是中文赛马的索引层。**

### 2.2 上游数据比想象中厚

二次核查实测（详见可行性报告 §7）：

| 数据 | 量 | 性质 |
| --- | ---: | --- |
| HKJC 中文公告总量 | 19,368 篇（2017-07 ~ 2026-11） | 全量可枚举 |
| 出马表（标题含「出賽馬匹名單」） | **956 篇** | 双语对照，核心语料 |
| 篇均出赛记录 | 约 **79 条**（实测 1–8 场/篇） | 推算总量 **约 7.5 万条 entry** |
| 参赛马匹简评 | 2,838 篇 | 纯中文逐马评述，**有中文名、无英文名** |
| 报名 / 退出 / 获选 / 优先 | 620 / 807 / 65 / 24 篇 | 赛前生命周期 |
| 晨操 / 试闸 / 兽医 | 340 / 311 / 822 篇 | 状态线内容 |

一份出马表附件的实际字段（2026-11-20 一哩冠军赛实测）：

```
抬头：一哩冠軍賽 (一級賽) - 一六○○米 草地 / 二○二六年十一月二十二日星期日 / 日本京都競馬場 / 海外賽事第一組 第一場
表头：馬號 | 配備 | Horse Name(产地) | 馬名 | 排位 | 國際評分 | 配磅 | 性別 | 年齡 | Trainer | 練馬師 | Jockey | 騎師
样例行：2 |  | Embroidery (JPN) | 巧繡生花 | 2 | 118 | 123 | F | 4 | Kazutomo Mori | 森一誠 | Christophe Lemaire | 李慕華
```

**一行 = 三名对照 + 六个事实字段。** 这就是天然的标注语料，且是人工校对过的。

### 2.3 与现有站点的关系

`kzn-web`（絆 · 绊崽档案）是**单一种马产驹**的深度档案，纵向深、横向窄。
马名通译是**跨地区、跨马匹**的横向索引，两者不冲突：

- 絆 → 马名通译：马匹页可外链到血统/产驹详情。
- 马名通译 → 絆：查某匹产驹时，跳到絆看它的兄弟姐妹与母系。
- 复用：Tailwind token、`i18n.js` 的日文→中文枚举、Python 管线的抓取/重试骨架、Cloudflare 部署配置。

**但代码仓独立**（新 repo），不跟着 `yunji-web` 母版同步，避免污染分支站的同步链。

## 3. 核心设计：名称是"带出处的声明"

这是全站最重要的一个决定。

### 3.1 三级译名 + 置信度

| 级别 | 来源 | 例 | 置信度 | 页面标识 |
| --- | --- | --- | --- | --- |
| L1 港译 | HKJC 公告附件（人工） | 名將田原 | 0.95 | 徽章「港译」 |
| L2 民间通译 | 大陆/台湾媒体、社区、马主冠名 | 名将田园 | 0.6 | 徽章「通行译名」 |
| L3 规则生成 | 冠名表 + 意译 + 音译 | 名将塔巴鲁 | 0.3 | 徽章「机器译名 · 待确认」 |

规则：**同一语言下 L1 存在则压过 L2/L3**；L3 永不覆盖已有 L1，只做补位；所有层级都保留 `source_url` 与 `decided_at`。

### 3.2 冠名表：L3 的真正核心

日本马名大量是「马主冠名 + 词」的结构。把冠名固定下来，机器译名的一致性会立刻从"随机音译"变成"像人译的"。

| 冠名 | 中文 | 冠名 | 中文 |
| --- | --- | --- | --- |
| Meisho | 名將 | Symboli | 象徵 |
| Agnes | 愛麗 | Daiwa | 大和 |
| Narita | 成田 | Hishi | 菱 |
| Sakura | 櫻花 | Admire | 愛慕 |
| Manhattan | 曼哈頓 | Tanino | 谷野 |
| Katsuragi | 葛城 | Stay Gold 系 | 黃金 |
| T M | 超強 | Meikei | 名駒 |

这套表约 200–400 条，可直接从港译语料里反推（同一冠名反复出现在英文名开头与中文名前缀），**自动抽取 + 人工确认**，是最容易做出差异化的资产。

### 3.3 名字要能"溯源"

马匹页上每个名字旁边一个来源标记，点开是一张卡片：

```
名將田原  港译
  来源：《一哩冠軍賽 – 最後宣佈出賽馬匹名單及排位》
  2026-11-20 · 香港赛马会赛马新闻 · 附件 FinalDecl_C.docx 第 12 行
  [查看原文]

Meisho Tabaru  原名（日）
  来源：netkeiba 马匹档案 2021103272
  [查看原文]
```

这一层看起来是"细节"，实际是**整个站的信任基础**——中文赛马圈最不缺的就是"你这个译名哪来的"。

## 4. 数据模型

SQLite 作工作库，构建期导出 JSON 分片给前端。

```sql
-- 赛事
race(race_uid PK, cn_name, en_name, local_name, country, racecourse,
     grade, distance_m, surface, race_date, race_no, going, prize,
     first_seen_at)

-- 赛事别名（同一赛事跨年、跨译名）
race_alias(race_uid, lang, name, type, confidence, source, decided_at)

-- 马匹
horse(horse_uid PK, cn_name_primary, birth_year, sex, country_code,
      colour, sire_uid, dam_uid, status)

-- 马匹名称（一马多名，全部保留）
horse_name(horse_uid, lang, value, script, type, confidence, source, decided_at)

-- 人物（骑师 / 练马师，同表分角色）
person(person_uid PK, role, cn_name, country)
person_name(person_uid, lang, value, type, confidence, source)

-- 出赛记录（核心事实表）
entry(race_uid, horse_uid, saddle_no, draw, jockey_uid, trainer_uid,
      weight_lb, intl_rating, gear, sex, age,
      finish, margin, finish_time, scraped_from, doc_url)

-- 外部 ID 映射
xid(entity_type, entity_uid, system, external_id)
-- system: netkeiba / jbis / racingpost / equibase / hkjc
```

两个设计要点：

1. **`horse_name` 是 1:N，不是字段。** 一匹马天然有多个名字（港译、旧译、民间、原名、罗马字），用字段存必然丢信息。
2. **`xid` 独立成表。** netkeiba 的 `horse_id` 是它自家的，不能当主键；以后接 JBIS、Racing Post 都往这张表塞，主键永远是 `horse_uid`。

## 5. 数据管线（6 段）

> 编号说明：本节按方案阶段编号（Stage 0–5）；`pipeline/README.md` 按脚本编号（S0–S5），
> 颗粒度更细（S2 抓取 / S3 解析 / S4 对齐 / S5 发布），执行以该文件为准。

### Stage 0 · 采集

- 全量枚举：`/wp-json/wp/v2/posts?per_page=100&orderby=id&order=asc`，194 页，**必须带退避重试**（连续快速请求会 400）。
- 分类：按标题正则分流出马表 / 简评 / 报名 / 退出 / 获选。
- 正文 + 附件一起落盘，按 `sha1` 去重。

### Stage 1 · 解析（最大的坑在这）

**三种形态，三条路径：**

| 形态 | 占比（抽样 40 篇） | 处理 |
| --- | ---: | --- |
| `.docx` 附件 | 约 1/3 | `python-docx` 直接读表 |
| `.doc` 附件（OLE2） | 约 1/3 | `soffice --headless --convert-to docx` 后转读 |
| 内联 HTML 表格 | 约 1/3 | `lxml` 抽 `<table>` |

**两个必须处理的坑：**

1. 附件是协议相对链接 `//res.hkjc.com/...`。主机名白名单：`res.hkjc.com`、`corporate.hkjc.com`、`racing.hkjc.com`；拼成 `racingnews.hkjc.com/wp-content/...` 会 **500**。
2. 表头是「中英同名双列」（`Trainer | 練馬師`），合并单元格和空列要先归一，否则列会错位。

输出统一成 `entry` 行 + `race` 抬头。

### Stage 2 · 对齐（日本优先，**仅日本**）

```
HKJC 英文赛事名 + 日期
   → netkeiba 日期列表 /race/list/YYYYMMDD/   （race_id 不编码日历日期，必须靠这层映射）
   → 候选 race_id（用 R 番号 + 距离 + 场地 + 匹数 四重校验）
   → 赛事页 18 匹 horse_id
   → 与 entry 的英文马名做集合匹配（Jaccard ≥ 0.7）
   → 写 xid(netkeiba, horse_uid)
```

对齐成功的判定要分三层，别用"跑通了"当结论：

| 层级 | 指标 | P0 目标 |
| --- | --- | --- |
| race 级 | 日本赛日公告 → race_id 命中率 | ≥ 90% |
| entry 级 | 单场马匹名匹配率 | ≥ 85% |
| 名称级 | 中英马名一致率（人工抽检 100 条） | ≥ 95% |

### Stage 3 · 名称归并

- 规范化：`upper` → 去 `(JPN)` → 去标点/连字符/所有格 → 去中文译名。
- 匹配：精确 → `rapidfuzz` 模糊（ratio ≥ 92）→ 人工队列。
- **消歧**：同名不同马（如各国都有 `Lucky`），用「产地 + 生年 + 练马师」三键排他。
- 归并结果写 `horse_name`，冲突进 `review_queue` 表，不自动合并。

### Stage 4 · 扩区

| 地区 | 主源 | 可用键 |
| --- | --- | --- |
| 日本 | netkeiba | race_id / horse_id（最完整） |
| 澳洲/新西兰 | Racing Australia、Arion | 英文名 + 日期 |
| 英国/爱尔兰 | Racing Post | 英文名 + 赛事 |
| 法国 | France Galop | 英文名 + 日期 |
| 美国 | Equibase | 英文名 + 日期 |

日以外的地区没有稳定公开 ID，主要靠「英文名 + 日期 + 赛事名」三键匹配，准确率会低一档——所以**先做日本，把方法跑顺再复制**。

**但"先做日本"只针对译名维护与 netkeiba 对齐，不针对抓取。** 956 篇公告全部抓、全部解析、
全部入 `entry` 表；非日本马以 `curation = pending` 落库，名字只用公告港译 + 原名，不做
L2/L3、不进 `review_queue`。这样扩区时不需要重抓，只是把 `curation` 翻成 `curated` 并补校对。

### Stage 5 · 发布

- SQLite → JSON 分片（每 500 实体一个文件）+ 轻量索引。
- 构建期生成静态页，搜索索引用 Pagefind。
- 增量：新增公告只重跑对应 race_uid 的解析与对齐。

## 6. 网站结构

```
/                          首页：搜索框 + 今日/近期赛事 + 最近更新的马匹
/race/{country}/{slug}     赛事页：中文名 / 原名 / 级别 / 距离 / 历届 / 本届出马表
/horse/{slug}              马匹页：中文名 + 原名 + 出身 + 战绩 + 同场关系
/jockey/{slug}             骑师页：胜场、关联马匹、代表赛事
/trainer/{slug}            练马师页
/name/{query}              译名对照：一个名字的全部分身
/calendar/{yyyy-mm}        赛历
/country/{jp|au|gb|fr|us}  地区页
/about/sources             数据来源与译名规则（信任页，必须有）
```

### 6.2 搜索

索引字段：中文名（繁/简）、拼音全拼、**拼音首字母**、英文名、日文名、别名。

- `bxjns` → 寶塚紀念賽
- `名将田原` → 名將田原 / メイショウタバル / Meisho Tabaru
- `Meisho Tabaru` → 同一页

繁简双向用 OpenCC 在索引期展开，不做运行时转换。

## 7. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 采集/解析 | Python + httpx + lxml + python-docx | 与现有 `scripts/` 同语言，重试/限速骨架可复用 |
| `.doc` 转换 | LibreOffice headless | antiword 对表格支持太差 |
| 工作库 | SQLite | 单文件、可版本化、导出方便 |
| 站点 | **Astro + Tailwind** | 页面多、内容型、SEO 关键；静态输出，无需运行时 |
| 搜索 | Pagefind | 构建期索引，纯静态，中文分词够用 |
| 部署 | Cloudflare Pages | 仓库已有 `wrangler.jsonc`，与现站同一套 |

**为什么不沿用 Vite 多页**：现有站是「少量页面 + JS 渲染」，马名通译是「上万实体页 + 需要被搜索引擎收录」，静态生成 + 每页独立 HTML 是硬需求。Tailwind token 和 `i18n.js` 可以搬。

## 8. 分期路线

| 阶段 | 内容 | 产出 | 验收 |
| --- | --- | --- | --- |
| **P0**（2 周） | **956 篇全量解析（全地区，不按地区过滤）**；netkeiba 只对齐日本；译名维护只做日本马 | SQLite + 三张对照 CSV | race 级 ≥90%、entry 级 ≥85% |
| **P1**（2 周） | 静态站上线：赛事页 / 马匹页 / 译名对照 / 搜索（全量数据，非日本马标注「港译 · 未复核」） | 约 3000 页可访问 | 搜索零结果率 <10% |

| **P3**（持续） | 关系图、时间线、译名纠错（用户提交 + 审核） | 社区层 | 每月新增译名 ≥200 条 |

"先抓哪个地区"省不下多少时间；但漏抓的公告日后要补，得重跑索引、重对日期，代价更高。
真正贵的是人工译名校对——所以只把**维护**限制在日本，**抓取**不设限。数据在库里等着，
扩区时只改 `horse.curation`。

**P0 就能验证的事**：956 篇全解析 + 日本 G1 全量译名核对，够撑起一个"能查"的站。不必等
全地区译名都做完再上线。

## 9. 风险与红线

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **版权** | 出马表附件、简评正文都是 HKJC 版权内容 | 只存**事实字段**（马名/号码/磅重/名次）与**名称对照**；简评不转载原文，改写为结构化摘要；每页署名来源 |
| **商标** | 不得暗示官方 | 站名、logo、文案均不出现马会标识；来源页明确"非官方" |
| **博彩合规** | 面向大陆用户，涉赌风险高 | 不做赔率、不做贴士、不做投注入口、不做赛果预测；定位"资料库" |
| **数据源稳定** | 站点改版、限流、附件迁移 | 原件只作解析中间件；对外引用走 Internet Archive 回放（`archive` 表）；按 race_uid 增量；HKJC ≥2s/请求、netkeiba ≥5s/请求 |
| **netkeiba 条款** | 无 robots 规则，无公开 API | 低频只读、只取必要页、缓存优先；产品化前评估授权 |
| **译名争议** | 一名多译、一译多名 | 多来源并列 + 置信度 + 可溯源，不做"唯一正确答案" |
| **名称歧义** | 同名不同马 | 产地 + 生年 + 练马师 三键消歧，冲突不自动合并 |

**一条底线**：宁可不收，不可猜。L3 机器译名必须显式标注「待确认」，不能混进 L1 里。

### 12.2 为什么叫 `maming-tongyi` 而不是中文或 `mmty`

- GitHub 仓库名只能是 ASCII，中文名无法用；拼音全拼可读性最好。

### 12.3 仓库设置（Settings 里勾）

| 位置 | 设置 | 原因 |

| General → Default branch | `main` | — |

### 12.4 部署方式与 base 路径（最容易踩的坑）

项目页 URL 是 `https://<user>.github.io/maming-tongyi/`，站点挂在**子路径**下。两条路：

- **绑自定义域名**（推荐）：`astro.config.mjs` 里 `site: 'https://maming.racing'`、`base: '/'`，加 `public/CNAME`。路径最干净。
- **不绑域名**：必须 `base: '/maming-tongyi/'`，且所有内部链接走 `import.meta.env.BASE_URL` 拼，否则上线全 404——这是 Astro/GH Pages 最常见的翻车点。

**建议 P0 就先把域名定下来**，省得后面改一遍全站链接。
